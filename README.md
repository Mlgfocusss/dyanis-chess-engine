# Dyanis — chess engine

Собственный шахматный движок на Go. Разрабатывается и тестируется
локально (CLI, perft-тесты), компилируется в WebAssembly и подключён
к React-фронтенду (без бэкенд-сервера — статичный деплой на GitHub
Pages / Vercel).

## Быстрый старт

```bash
# Поиграть в терминале (SAN: e4, Nf3, O-O — или координаты e2e4)
go run ./cmd/cli -play -depth 4
```

```bash
# Запустить React-доску в браузере (после первой сборки wasm — см. ниже)
cd web && npm install && npm run dev
```

```powershell
# Пересобрать wasm после правок в cmd/wasm/main.go или internal/ (PowerShell)
$env:GOOS="js"; $env:GOARCH="wasm"; go build -o cmd/wasm/dyanis.wasm ./cmd/wasm
```
```bash
# То же самое в bash/zsh
GOOS=js GOARCH=wasm go build -o cmd/wasm/dyanis.wasm ./cmd/wasm
```

Подробности, флаги и что скопировать перед первым запуском — в
разделе "Как запустить" ниже.

## Статус

- [x] Шаг 1 — представление доски и генерация ходов
      (включая рокировку, взятие на проходе, превращение пешки)
- [x] Шаг 2 — perft-тесты (стартовая позиция + Kiwipete)
- [x] Шаг 3 — minimax + alpha-beta (негамакс), фиксированная глубина
- [x] Шаг 4 — оценочная функция: материал + piece-square tables
      (таблицы Michniewski; отдельные midgame/endgame таблицы и
      tapering по фазе игры — только для короля)
- [x] Шаг 4.5 — книга дебютов (Polyglot .bin): Zobrist-хеширование,
      чтение/декодирование `.bin`, взвешенный выбор хода, подключена
      к поиску как приоритетная проверка перед запуском negamax.
      Можно подключить НЕСКОЛЬКО книг цепочкой по приоритету
      (`book.Chain`/`book.Source` в `internal/book/book.go`): первая
      книга, где для позиции нашлась хоть одна запись, "выигрывает" —
      дальше по цепочке не идём. Веса разных книг намеренно НЕ
      смешиваются (см. заметку в конце) — только fallback.
- [x] Шаг 5 — UCI-протокол (uci/isready/position/go/quit, книга подключена, SAN в -play)
- [x] Шаг 6 — итеративное углубление и таймер
- [x] Шаг 7 — компиляция в WASM (`cmd/wasm`), JS-API `window.Dyanis`
- [x] Шаг 8 — React-доска (`web/`): drag&drop + клик-клик
      (`react-chessboard`), поиск ходов в отдельном Web Worker (не
      блокирует страницу даже на большой глубине без лимита времени),
      книга дебютов из браузера, выбор стороны/глубины/бюджета времени
- [x] Шаг 9 — усиление поиска и оценки после первой рабочей версии:
      - quiescence search (борьба с horizon effect — досматривает
        взятия и шаховые серии за пределами номинальной глубины)
      - move ordering: TT-ход → MVV-LVA → killer moves → history heuristic
      - null-move pruning (с защитой от цугцванга и от отсечения в корне)
      - оценочная функция расширена: mobility, пешечная структура
        (сдвоенные/изолированные/проходные), king safety (пешечный щит
        + открытые линии, taper по фазе), пара слонов, mop-up eval
        (загон голого/слабого короля к краю в выигранных эндшпилях)
- [x] Шаг 9.5 — ничьи по правилам (были единственной дырой из
      README-заметки ниже): 50-move rule и троекратное повторение.
      50-move проверяется прямо внутри `negamax`/`quiescence` через
      `board.HalfmoveClock` (self-contained, без истории). Repetition
      принципиально нуждается в истории партии, поэтому живёт на
      уровне игровых циклов — `GameStatusWithHistory` в
      `movegen/status.go`, подключена в CLI (`-play`), wasm
      (`Dyanis.getState`/`buildState`) и UCI (`info string` перед
      `bestmove`, не блокирует ответ — решение объявлять ничью
      формально остаётся за GUI/арбитром). Внутри самого дерева
      поиска repetition НЕ детектится (это отдельная, более
      инвазивная задача — протаскивать историю позиций через всю
      рекурсию `negamax`), но это не баг: конечная по глубине search-
      дерево не может зациклиться так, как это может бесконечная
      реальная партия.
- [x] Шаг 9.6 — три точечных техдолга, закрытых за один заход:
      - **mate-distance adjustment**: `negamax` теперь знает `ply`
        (глубину от корня) и возвращает `ply - MateScore` вместо
        плоского `-MateScore` — мат в 1 ход больше не выглядит для
        alpha-beta так же, как мат в 5. Заодно починена реальная TT-
        дыра: раньше закешированный mate-score из одного пути к
        позиции мог тихо переиспользоваться на другом (по
        транспозиции) пути с другой дистанцией до мата —
        `storeAdjustMateScore`/`readAdjustMateScore` в `search.go`
        конвертируют между "root-relative" и "node-relative"
        представлением при записи/чтении TT
      - **insufficient material**: `movegen.InsufficientMaterial` —
        K vs K, K+лёгкая vs K, K+B vs K+B с одноцветными слонами.
        Самодостаточная проверка (без истории партии), подключена и в
        `GameStatus` (значит бесплатно долетает до CLI/wasm/UCI через
        уже существующий `GameStatusWithHistory`), и напрямую в
        `quiescenceSearch`
      - **инкрементальный Zobrist-хеш**: `Board.Hash()` больше не
        пересчитывается с нуля на каждый вызов — теперь это поле
        `Board`, которое `MakeMove`/`MakeNullMove` поддерживают через
        точечные XOR (фигуры, права на рокировку, en passant, сторона
        хода). `Board.VerifyHash()` — сверка с полным пересчётом,
        для тестов
- [ ] Шаг 10 — то, что осталось из классики: PVS/NegaScout, aspiration
      windows, LMR, SEE

## Первым делом

Замени `github.com/yourname/dyanis-chess-engine` в `go.mod` и во всех
импортах на свой реальный путь (например `github.com/<твой-ник>/dyanis-chess-engine`),
если планируешь публиковать репозиторий под своим именем.

## Как запустить

### CLI (локальная разработка/отладка)

```bash
# Все тесты (включая perft на стартовой позиции и Kiwipete)
go test ./...

# То же самое, но без медленного perft depth=5
go test ./... -short

# Напечатать стартовую позицию
go run ./cmd/cli

# Напечатать произвольную позицию по FEN
go run ./cmd/cli -fen "r3k2r/p1ppqpb1/bn2pnp1/3PN3/1p2P3/2N2Q1p/PPPBBPPP/R3K2R w KQkq - 0 1"

# Perft с разбивкой по ходам (полезно для отладки генератора ходов —
# сверяй total с эталонными числами, см. internal/perft/perft_test.go)
go run ./cmd/cli -perft 3

# Интерактивная игра в терминале против движка.
# Ходы вводятся в обычной шахматной нотации: e4, Nf3, O-O, exd5, e8=Q —
# координатная запись (e2e4) тоже по-прежнему работает.
#
# По умолчанию -play подключает книгу дебютов assets/gm2001.bin, если
# файл на месте (см. "Опционально" ниже, откуда его скачать) — пока
# текущая позиция есть в книге, движок играет из неё мгновенно, без
# поиска. Если файла нет — не ошибка, просто предупреждение в stderr
# и игра идёт без книги.
go run ./cmd/cli -play -depth 4

# -book принимает СПИСОК путей через запятую, в порядке приоритета:
# первая книга, где для текущей позиции нашлась запись, играет ход;
# следующие книги в списке проверяются только если предыдущие вообще
# не видели эту позицию (см. book.Chain в internal/book/book.go —
# веса разных книг НЕ смешиваются, это принципиально, см. заметку
# в конце README). Путь, который не удалось загрузить (опечатка,
# битый файл), просто пропускается с предупреждением — остальные
# книги из списка это не ломает.
go run ./cmd/cli -play -depth 4 -book "assets/gm2001.bin,assets/komodo.bin,assets/performance.bin"

# Явно отключить книгу вообще, даже если assets/gm2001.bin существует:
go run ./cmd/cli -play -depth 4 -book ""

# Как UCI-движок поверх stdin/stdout (Arena, CuteChess и т.п.)
go run ./cmd/cli -uci
```

По завершении партии (мат/пат) в `-play` печатается полный лог в
стандартной нотации вида `1. e4 c5 2. Nf3 Nc6 3. ...`.

### WASM-сборка (`cmd/wasm`)

```powershell
# PowerShell:
$env:GOOS="js"; $env:GOARCH="wasm"; go build -o cmd/wasm/dyanis.wasm ./cmd/wasm
```

```bash
# bash/zsh:
GOOS=js GOARCH=wasm go build -o cmd/wasm/dyanis.wasm ./cmd/wasm
```

`wasm_exec.js` (копия из установки Go, обычно `$(go env GOROOT)/lib/wasm/wasm_exec.js`
на Go ≥1.24 или `misc/wasm/wasm_exec.js` на более старых) уже лежит
рядом в `cmd/wasm/`.

Быстрая ручная проверка сборки (не финальный UI, просто smoke-test —
подробности в `cmd/wasm/README.md`):

```powershell
py -m http.server 8000   # из корня репозитория, не из cmd/wasm
```
→ http://localhost:8000/cmd/wasm/

### React-доска (`web/`)

```bash
cd web
npm install
npm run dev
```

Перед первым запуском скопируй в `web/public/`:
- `cmd/wasm/dyanis.wasm` и `cmd/wasm/wasm_exec.js` → в `web/public/wasm/`
- книги дебютов (`assets/gm2001.bin`, `assets/komodo.bin`,
  `assets/performance.bin` — какие есть) → в `web/public/assets/`.
  Браузер не видит файловую систему репозитория, поэтому файлы должны
  физически лежать в двух местах: `assets/` (читает CLI/UCI с диска)
  и `web/public/assets/` (читает браузер через `fetch()`). Порядок
  приоритета задаётся не именем файла, а порядком вызовов
  `Dyanis.loadBook(...)` на фронте — см. `jsLoadBook` в
  `cmd/wasm/main.go`.

Поиск ходов работает в отдельном Web Worker (`web/public/engine-worker.js`)
со своей независимой копией wasm-модуля — страница не подвисает,
сколько бы движок ни думал, даже на большой глубине без ограничения
по времени. Подробности архитектуры — в комментариях
`web/src/engine/dyanisEngine.js`.

### Опционально: книга дебютов

`-play` без `assets/gm2001.bin` работает и так — книга просто
пропускается с предупреждением. Чтобы включить её, скачай любой
Polyglot-совместимый `.bin` (например `gm2001.bin`, `komodo.bin` —
доступны в открытых репозиториях с шахматными книгами) и положи в
`assets/`. Можно положить несколько файлов сразу и подключить их
цепочкой по приоритету через `-book` (см. пример выше) — для браузера
не забудь продублировать те же файлы в `web/public/assets/` (см.
секцию про React-доску выше).

## Архитектурные заметки

- **Board.MakeMove копирует доску**, а не делает make/unmake с откатом.
  Это проще и надёжнее на этапе, пока важна корректность (perft), а не
  скорость. Профилировать и, если нужно, переходить на make/unmake —
  отдельная задача на будущее, когда движок уже играет.
- **internal/** — все пакеты недоступны для импорта извне модуля.
  Осознанно: движок ещё не публичный API.
- Массив `[64]Piece` — простое представление на старте. Если позже
  понадобятся битборды для скорости, `movegen`/`search` не должны
  трогаться — они работают через методы `Board`, а не напрямую с полем
  `Squares`.
- **Книга дебютов проверяется до поиска, не внутри eval.** Вес хода в
  книге ничего не говорит о статичной оценке произвольной позиции
  глубоко в дереве поиска — это решение уровня "какой ход играть
  прямо сейчас", поэтому оно живёт как проверка в самом начале
  `search.BestMoveWithBook`, а не как слагаемое в `eval.Evaluate`.
- **Несколько книг подключаются цепочкой (`book.Chain`), а не
  слиянием записей.** `Entry.Weight` — это относительная частота
  *внутри одной конкретной книги*, а не нормализованная вероятность;
  слить записи `gm2001.bin` и `komodo.bin` в один список и выбирать
  по сырому весу значило бы случайно фаворитизировать ту книгу, чей
  составитель использовал бо́льшие числа — без всякого шахматного
  смысла за этим. Вместо этого `Chain.LookupBoard` пробует книги по
  порядку приоритета и возвращает записи первой, где для позиции
  вообще что-то нашлось; остальные книги в цепочке для этой позиции
  не смотрятся вовсе. `search.BestMoveWithBook` принимает интерфейс
  `book.Source` (реализуют и `*Book`, и `*Chain`), так что вызывающему
  коду всё равно, одна книга подключена или несколько.
- **50-move rule детектится прямо в `search.go`, без истории партии**
  — `board.HalfmoveClock` уже обновляется в `MakeMove`, так что
  `negamax`/`quiescenceSearch` просто читают его напрямую и трактуют
  `>= 100` как ничью. Троекратное повторение принципиально устроено
  иначе: положению нужно видеть историю партии, которой у одиночного
  `*board.Board` нет и быть не может — поэтому оно живёт отдельной
  функцией `movegen.GameStatusWithHistory` на уровне игровых циклов
  (не внутри самого поиска — см. следующую заметку).
- **CLI, wasm и UCI по-разному копят историю позиций для
  repetition — и это осознанно, а не рассинхрон.** CLI (`playInteractive`)
  и wasm (`game.history`) сами ведут партию от начала до конца, поэтому
  наращивают историю инкрементально, на каждый сделанный ход. UCI
  устроен иначе: GUI при каждой команде `position ...` присылает ПОЛНЫЙ
  список ходов от `startpos`/`fen`, а не только новые — так что
  `session.history` в `uci.go` каждый раз пересобирается с нуля вместе
  с позицией, а не дополняется.
- **Repetition НЕ детектится внутри самого дерева поиска** — только на
  уровне игровых циклов, описанных выше. Это осознанное упрощение, а
  не баг: полноценная версия потребовала бы протаскивать историю
  позиций через всю рекурсию `negamax` (и менять сигнатуры
  `BestMove`/`BestMoveTimed` под это) — отдельная, более инвазивная
  задача на будущее. Конечное по глубине дерево поиска не может
  зациклиться так, как может бесконечная реальная партия, так что
  отсутствие этой проверки не создаёт того бага, который решался в
  шаге 9.5 — просто иногда чуть менее точная оценка линий, которые
  транспонируются обратно в уже виденную позицию.
- **`Board.Hash()` — просто чтение поля, не пересчёт.** Хеш
  поддерживается инкрементально: `MakeMove`/`MakeNullMove` точечно
  XOR'ят только то, что реально изменилось (сдвинутые/взятые фигуры,
  отозванные права на рокировку, старый/новый en passant, сторона
  хода), вместо обхода всех 64 клеток на каждый вызов. Полный пересчёт
  (`computeHashFromScratch`) остался только там, где хеш неоткуда
  взять инкрементально — `NewInitialBoard`/`FromFEN`, когда `Board`
  строится с нуля, а не выводится из другого `Board` через
  `MakeMove`/`Copy`. `Board.VerifyHash()` сверяет текущее поле с
  полным пересчётом — стоит гонять его по perft-дереву позиций
  (глубина 4-5 от старта и от Kiwipete) после любой правки `MakeMove`,
  которая трогает хеш: там легко словить тихий баг именно на
  en passant или обнулении прав на рокировку.
- **Mate-distance adjustment: `negamax` возвращает `ply - MateScore`,
  не плоский `-MateScore`.** `ply` — глубина от корня поиска (0 в
  корне, +1 на каждый рекурсивный вызов, включая null-move пробу).
  Без этого мат в 1 ход и мат в 5 ходов давали бы совершенно
  одинаковый счёт, и alpha-beta не могла бы предпочесть более быстрый
  мат более медленному (или, с другой стороны доски, максимально
  оттянуть неизбежный мат). Важнее для корректности: транспозиционная
  таблица кеширует mate-score в "node-relative" виде через
  `storeAdjustMateScore` (не зависящем от того, каким путём пришли к
  позиции), а при чтении `readAdjustMateScore` конвертирует обратно
  под текущий `ply` — раньше без этой пары функций закешированное
  значение с одной дистанции до мата могло тихо подставиться на
  другую дистанцию при транспозиции в ту же позицию другим путём.
- **`InsufficientMaterial` — намеренно упрощённое правило, не полная
  dead-position детекция.** Покрывает только K vs K, K+лёгкая vs K,
  K+B vs K+B с одноцветными слонами — комбинации вроде K+N+N vs K
  (обычно ничейные на практике, но не по строгим правилам ФИДЕ) или
  "мёртвые" позиции с пешками на доске сознательно не покрываются: это
  требует позиционного анализа, а не просто подсчёта материала.
- **Quiescence search** (`search.go`, `quiescence`/`quiescenceSearch`)
  досматривает взятия (и, с ограниченным бюджетом, шаховые серии) за
  пределами номинальной глубины — без этого негамакс на границе
  глубины может остановиться прямо посреди размена и посчитать
  "выиграл пешку", хотя следующим ходом фигуру отбивают обратно.
- **Move ordering** (там же) — TT-ход, затем взятия по MVV-LVA
  (Most Valuable Victim, Least Valuable Attacker), затем killer moves
  (тихие ходы, давшие отсечение на этой же глубине в соседней
  позиции), затем всё остальное по history heuristic. От этого впрямую
  зависит эффективность alpha-beta отсечений.
- **Null-move pruning** — "а что если пропустить ход, всё равно ли
  сопернику плохо?" с защитой от цугцванга (`hasNonPawnMaterial`) и от
  срабатывания прямо в корне дерева (параметр `isRoot` у `negamax`,
  иначе `BestMove` не получит вычисленный лучший ход).
- **Mop-up eval** (`eval/mopup.go`) — в выигранных эндшпилях (перевес
  ≥ ~500cp) остальные слагаемые eval быстро насыщаются и перестают
  различать ходы, из-за чего движок может бесконечно "шаркать"
  фигурами вместо того, чтобы доводить мат. Этот термин создаёт явный
  градиент: гони слабого короля к краю, приближай своего короля ему
  на помощь.
- **`dyanis.wasm` не коммитится в git** — это собранный артефакт,
  пересобирается из `cmd/wasm/main.go` командой выше. См. `.gitignore`.
- **wasm использует ДВА независимых экземпляра модуля** — один в
  основном потоке страницы (быстрая бухгалтерия партии: ходы, история,
  undo, никогда не блокирует), второй в отдельном Web Worker (только
  поиск, полностью изолирован по памяти от первого). Именно поэтому у
  `window.Dyanis` есть стейтлесс-функция `searchMove(fen, depth,
  movetimeMs)` отдельно от завязанного на внутреннее состояние партии
  `engineMove()` — воркеру неоткуда взять текущую позицию иначе, кроме
  как явным параметром. Решённый ход воркер только *предлагает*;
  применяет его к реальному состоянию партии всегда основной поток,
  тем же вызовом `makeMove`, что и для хода человека.
